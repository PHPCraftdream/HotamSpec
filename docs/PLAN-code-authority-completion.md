## Часть 1. Целостная картина

### 1.1. У фреймворка две половины, и они разной зрелости

Формулировка цели — «объекты, поля, методы, тесты, которые генерируют доки» — распадается на два независимых механизма, и они построены неравномерно:

**Половина ДОКАЗАТЕЛЬСТВА (сильная, реальная, механически принуждённая).** Требование не может соврать о том, что оно доказано:

| гейт | что реально делает |
|---|---|
| `check_verified_by_test_passes` | по-настоящему запускает `go test`, требует зелёный бар `[П]` |
| `check_scenario_executes_impl` | под `-coverprofile` проверяет, что тест реально исполняет строки `implemented_by`-символа `[П]` |
| `check_settled_requires_scenario` | блокирует `apply-proposal` для SETTLED без носителя `[Р]` |
| `check_spec_md_current` | полный re-render SPEC.md, устаревание = violation `[П]` |
| `check_discipline_ratchet` | `discipline:full` необратим, пин в `graph.lock` `[Р]` |
| `check_model_complete` | полнота модели по методам, упомянутым в `implemented_by` `[Р]` |

Это не декларация — это шесть работающих механизмов. **Эту половину переделывать не нужно.**

**Половина МОДЕЛИ (частичная).** «Объекты, поля, методы» извлекаются из Go AST в `MODELS.md`, но извлекается только часть публичной поверхности:

- есть: exported top-level types, struct fields, receiver methods, `Err*`
- нет: **методы интерфейсов** (а значит — контракты портов и моков внешнего мира), конструкторы и top-level функции, константы и enum-значения, doc-комментарии полей, struct tags, обязательность/уникальность/валидационные ограничения

Для «любой ИС» отсутствие методов интерфейсов — самый тяжёлый пробел: именно интерфейс описывает границу с внешним миром, и именно он в `MODELS.md` выглядит пустым.

### 1.2. Точная природа регрессии: израсходованный opt-in

Это не «чек слишком строгий». Это нарушение собственного закона фреймворка.

`R-scenario-spec-obligations-mechanically-enforced` (`internal/selfspec/requirements_authoredspec.go:119`) `[П]` дословно гласит:

> «Each gate is an honest no-op before its own opt-in trigger fires (no discipline:full, no SPEC.md, no authored-path pair), so the migration is per-domain and carries no long-lived opt-out flag»
> «the `discipline:"full"` flip lands in the same commit that completes a domain's migration»

Задача #369 (коммит `0f90ad7`) добавила ШЕСТОЙ гейт — `check_claim_matches_scenario` — в тот же самый триггер `discipline:"full"`. Но PRAT и GPSM флипнули этот флаг задолго до, соглашаясь на четыре гейта того времени. **Opt-in однонаправлен и одноразов: домен, уже израсходовавший триггер, не может согласиться на обязанность, которой тогда не существовало.**

Последствия, замеренные:
- `PRAT-hotam/domains/prat` — 20 нарушений, из них 19 × `check_claim_matches_scenario` `[П]`
- `PRAT-hotam/domains/gpsm-sm` — 23 нарушения, из них 22 того же чека `[Р]`
- пути исправления нет: `sync-domain` отказывается работать без `spec/registrydump`, которого у этих доменов нет; `apply-proposal`/`land` не помогут — чек помечен `ComparesOnDiskProjection: true` и исключён из proposal-гейта; правка `graph.json` руками запрещена `R-no-hand-edit-graph` `[Р]`

**Отсюда — новый методологический закон, который стоит анкорить как требование:** израсходованный opt-in-триггер закрыт; новая обязанность требует НОВОГО триггера. Иначе апгрейд движка ретроактивно ломает согласившиеся домены.

### 1.3. Деривация Claim не готова к употреблению даже там, где её захотят

`deriveClaimFromVerifiedBy` конкатенирует заголовки без дедупликации `[Р]`. Реальный вывод для `R-gate-pg0-source-ready`:

> «SourceReady() only returns nil when columns, scope, and the project profile are ALL present **×4** Approve refuses to set ApprovedByPM…»

Одно предложение четыре раза. До исправления этого мигрировать на деривацию нельзя никому.

### 1.4. Два несвязанных каталога объектов

`EntityType` в графе → `ENTITIES.md`; Go-тип в `spec/model` → `MODELS.md`. Формальной связи нет `[Р]`. В GPSM в графе несколько крупных entity types, в `MODELS.md` — десятки объектов. ИИ-эксперт не может понять, расхождение это, разный уровень абстракции или норма.

Направление разрешения задано целью резолвера: **источник — Go-код**. Но действующее SETTLED-требование `R-generations-inherit-doc-test-code` `[П]` требует противоположного:

> «EVERY EntityType MUST yield a Go struct, its lifecycle methods, and transition tests»

и держит это как «honest REMAINING debt». Это долг, направленный в противоположную сторону от цели. Его половину про EntityType нужно не «закрывать», а **отклонить и заменить** обратным утверждением (Go-тип первичен, `EntityType` — его проекция либо ссылка).

### 1.5. Один тип узла делает три работы

`Requirement` сейчас несёт одновременно:

1. **нормативное утверждение** — «sign-off отклоняется при незакрытом блокере» (доказуемо тестом)
2. **элемент скоупа** — «R-FR-27 Чат бот в Telegram», «R-FR-07 Таблицы с историей запросов» (ОТТ заказчика; это вход в проектирование, не выход из исполнения — тест его никогда не породит и не должен)
3. **запись решения** — регуляторные ссылки, глоссарные термины

`INHERENTLY_PROSE` (14–35% SETTLED по доменам `[Р]`) прячет все три случая в одну корзину и одновременно служит дырой в принуждении: любое неудобное требование конвертируется в PROSE и домен зеленеет.

Развести эти три роли — самая глубокая из отложенных задач (высокий blast radius, не для P0).

### 1.6. Честная переформулировка цели

Строгое «в выходе только то, что создают тестовые прогоны» толкает движок заменять бизнес-формулировку заголовком теста — и порождает мусор вида «SourceReady() only returns nil… ×4» вместо «Gate P-G0 проверяется ДО начала Planning».

Формулировка, которая сохраняет всю силу замысла и при этом описывает реальность:

> **Доказательная часть (Given/When/Then/Value, proof state, покрытие) — 100% из реальных прогонов, никогда не пишется руками. Нормативный текст остаётся авторским, но механически привязан: он не может пережить удаление или покраснение своего теста, не может ссылаться на несуществующий символ и не может остаться без доказательства.**

Сдвиг: не «claim = заголовок теста», а «claim не может существовать без зелёного доказательства рядом». Три из шести уже работающих гейтов ровно это и делают.

Для домена, который ХОЧЕТ полной деривации, она остаётся доступной — но как явно выбранный режим (`claim_authority: "scenario"`), а не как то, что случается при апгрейде движка.

## Часть 2. Волны

### W0 — Остановить кровотечение (P0)

Пять дефектов: один ломает боевые домены прямо сейчас, два рискуют данными, два — дыры в модели.

**W0.1. Ввести `claim_authority` и снять exact-drift со всех `discipline:full`.**
Новый ключ manifest: `claim_authority: "authored" | "scenario"`, по умолчанию `"authored"`. `check_claim_matches_scenario` работает ТОЛЬКО при `"scenario"`. Флаг — однонаправленный ratchet по образцу `discipline` (пин в `graph.lock`, `check_discipline_ratchet`-подобная защита). Прогнать `all-violations` на `prat` и `gpsm-sm` — обязаны стать зелёными без единой правки их графов.
Одновременно — анкорить новый закон отдельным требованием: *израсходованный opt-in-триггер закрыт для новых обязанностей; новая обязанность требует нового триггера*, с `enforced_by` (см. W0.1b ниже, если механизируемо) либо честно PROSE.

**W0.2. Дедуп в деривации Claim.**
`deriveClaimFromVerifiedBy` (`internal/selfspec/claim_derive.go`) — убрать повторы заголовков, сохранив порядок `verified_by`. Тест на fixture с несколькими подсценариями одного заголовка. Без этого W0.1's режим `"scenario"` непригоден.

**W0.3. `Why` в вендоренном зеркале + regression-тест.**
`internal/ontology/canon/requirement.go` не содержит `Why` `[П]`, при этом `MergeIntoGraph` (`internal/selfspec/merge.go:73`, `merged := *entry`) относит `Why` к структурным полям, заменяемым из registry `[П]`. Домен, перешедший на `requirements_authority: code` с ручным `Why` в графе, при первом `sync-domain` молча получит `Why: ""`. Добавить поле в канон + e2e-тест, что `Why` переживает round-trip (текущий e2e проверяет `Claim` и `History`, но не `Why` `[Р]`).

**W0.4. Исключить вендоренное/сгенерированное из authored model scan.**
`ScanAuthoredModels` (`internal/gate/model_scan.go`) имеет баннер-детекцию только для вендоренного recorder'а `[П]`; для `spec/hotamontology/` (от `vendor-ontology`) и `spec/registrydump/` (от `scaffold-registrydump`) исключения нет. Служебные `Relation`/`Requirement`/`Registry` попадут в `MODELS.md` как доменные объекты. Ввести ЕДИНУЮ маркировку generated/vendor-файлов и одно общее правило исключения (не третий частный случай).

**W0.5. `ProposedGoal` и `ProposedEntityInstance`.**
Оба типа узлов не имеют ни Go-, ни JSON-пути записи `[Р]` — при том что для `EntityInstance` существуют 4 валидирующих инварианта, проверяющих узлы, которые нечем создать. Либо добавить kind'ы в `internal/proposal/types.go`, либо честно удалить осиротевшие инварианты. Решение резолвера.

### W1 — Достроить модельную половину (ядро цели резолвера)

**W1.1. Полнота AST-скана.**
Добавить в `internal/gate/model_scan.go`: методы интерфейсов (приоритет №1 — контракты портов/моков), конструкторы и top-level доменные функции, константы и enum-значения, doc-комментарии полей, struct tags и выводимые из них ограничения (обязательность, уникальность, валидация).

**W1.2. Mock/port как first-class разновидность модели.**
Классификация `object / value / port / mock / policy` без изменения их исполняемой природы. Моки — не временная подмена, а правильные исполняемые суррогаты внешнего мира; в `MODELS.md` они должны быть видны вместе с контрактом интерфейса и своими сценариями.

**W1.3. Связать `EntityType` с Go-символом; развернуть `R-generations-inherit-doc-test-code`.**
Либо поле `model_symbol`/отношение `realized_by`, либо явный отказ от дублирующих graph-полей в code-authority профиле. Одновременно отклонить EntityType-половину `R-generations-inherit-doc-test-code` (она требует генерировать Go из EntityType — направление, обратное цели) и заменить обратным утверждением.

**W1.4. Симметричная полнота публичной поверхности.**
Сейчас `check_model_complete` контролирует только символы, уже упомянутые в `implemented_by` `[Р]`: публичный объект или метод, который никто не связал с требованием, остаётся вне проверки. Ввести обратный инвариант: каждый публичный authored-символ либо связан с требованием и сценарием, либо явно помечен infrastructure/ignored с причиной.

**W1.5. Quality gate сценария.**
Наличие сценария определяется по вызову `hotamspec.NewScenario`, содержательность не требуется `[Р]` — почти пустой сценарий формально закрывает проверки. Минимум: непустой title, точный requirement ID, хотя бы один `Then`, для поведенческого — порядок `Given → When → Then`, явное исключение для декларативного/инвариантного.

### W2 — Сделать доказательство видимым и дешёвым

**W2.1. Включить `RequirementState()` во все requirement-представления.**
Вычисляемый lifecycle (`NO_CARRIER / UNVERIFIED / FAILING / STALE / PROVEN`) существует, но production-путь его почти не использует `[Р]`. Состояние должно быть видно рядом с каждым требованием. **Осторожно:** задача #317 намеренно сделала `TRACEABILITY.md`/`COVERAGE.md` execution-independent ради идемпотентности `hotam land` — включать состояние туда нельзя без явного решения; начинать с `hotam req`/`brief`.

**W2.2. Компактный evidence packet одним запросом.**
`requirement → why/status/conflicts/assumptions → сигнатуры объектов и методов → контракт порта/мока → Given/When/Then → proof state/свежесть/происхождение → связанные entity и process`. Сейчас ИИ вынужден читать граф, код, доки и тесты по отдельности — отсюда дорогой cold start (~54k токенов, 8.6 tool calls, 60с на вопрос у Sonnet `[Р]`).

**W2.3. Версия движка и свежесть проекций между репозиториями.**
Consumer-доки уже отстают от текущего движка `[Р]`. Нужен version stamp схемы + проверка свежести.

### W3 — Проверить на реальном вертикальном срезе

**W3.1. Узкий срез `life`.**
Не широкая онтология «всей жизни», а: 5–7 объектов (`Person`, `Commitment`, `Project`, `CalendarBlock`, `Decision`, `Resource`, `Constraint`), один lifecycle, один внешний порт/мок (календарь), 5–10 требований, 5–10 сценариев с реальными конфликтами.

Критерии приёмки:
1. Ни один generated-документ не правится руками.
2. Нет несвязанного дублирования объекта в graph и Go.
3. Каждый публичный метод связан с требованием и сценарием либо явно исключён с причиной.
4. Мок виден в model docs вместе с методами интерфейса и сценариями.
5. ИИ отвечает на 15 подготовленных вопросов, не читая сырой граф и весь исходник.
6. Baseline: ≥90% фактической точности, медиана ≤5 чтений, ≤15k входных токенов на холодный вопрос.

Этот срез даст больше информации о пригодности методологии, чем дальнейшее расширение self-spec.

### W4 — Свести документацию с реальностью

- `CLAUDE.md` TRANSLATE-шаг предписывает править `internal/selfspec/requirements_<topic>.go`, а все 27 этих файлов несут баннер `// Code generated … DO NOT EDIT BY HAND`, причём генератор лежит в `.scratch/`, вне git `[Р]` — при свежем клоне регенерировать нечем.
- `docs/AUTHORED-SPEC-CONTRACT.md:244` «ручного текста в `docs/gen/` нет вообще» — реально ~8% нормативного тела на лучшем домене `[Р]`.
- `docs/AUTHORED-SPEC-CONTRACT.md:20-23` «фреймворк проверяется своей же дисциплиной против себя» — на self-домене три ключевых гейта выключены (нет `discipline:full`) `[Р]`. Либо флипнуть (не пройдёт: 289 из 302 требований без носителя), либо признать асимметрию в тексте.
- `README.md`/quickstart описывают стартовые Stakeholder/Requirement, которых пустой домен больше не создаёт `[Р]`; quickstart не объясняет code-authority путь; authored-spec contract не описывает `sync-domain`/`requirements_authority`.
- `check_method_matches_docstring` — `return nil`, пустышка в реестре из 115 чеков `[Р]`. Реализовать или удалить.

## Часть 3. Чего НЕ делать (анти-релитигация)

- **Не строить универсальную метамодель ИС заранее.** Commands/queries/events, API endpoints, роли/permissions, транзакции, временные ограничения, NFR, storage schema — добавлять first-class типы ТОЛЬКО по фактической потребности реального домена. Метамодель-впрок — известный способ утопить проект.
- **Не убирать моки.** Это правильные исполняемые суррогаты внешнего мира, а не костыль. Проблема не в их наличии, а в их непредставленности в доках (W1.1/W1.2).
- **Не откатывать code-authority.** Направление верное; сломан конкретный гейт, а не замысел.
- **Не возвращать генерацию кода из спеки** (`gen-code` отклонён, `docs/AUTHORED-SPEC-CONTRACT.md` §9). W1.3 разворачивает EntityType-половину `R-generations-inherit-doc-test-code` именно В СТОРОНУ authored-кода, а не обратно к генерации.
- **Не заменять авторский нормативный текст заголовком теста по умолчанию** — только в явно выбранном режиме `claim_authority: "scenario"`.

## Часть 4. Итоговая оценка

| измерение | оценка | комментарий |
|---|---:|---|
| доказательная половина (тест как доказательство) | 8/10 | реальный запуск, coverage-связь, шесть работающих гейтов |
| модельная половина (объекты/поля/методы в доках) | 5/10 | интерфейсы, конструкторы, константы, ограничения теряются |
| единый источник истины | 4/10 | graph, registry, Go AST, test artifacts не связаны формально |
| принуждение для нового домена | 5/10 | гейт настоящий, но обходится через DRAFT и INHERENTLY_PROSE |
| «доки только из тестов» в строгом чтении | 2–4/10 | ~8% нормативного тела на лучшем домене |
| охват «любой ИС» | 5/10 | в Go выразимо почти всё, но многие понятия ИС не first-class |

Фреймворк перешёл границу исследовательского прототипа: он хранит исполняемую предметную модель, проверяет сценарии и строит полезные документы; PRAT/GPSM это подтверждают. Но заявлять готовность к «любой информационной системе» рано — по причинам W0–W2 выше.

Правильный следующий шаг — не переписывать методологию: исправить W0, достроить модельную половину W1, и сразу проверить на узком жизненном срезе W3.
